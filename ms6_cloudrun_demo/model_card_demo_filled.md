# Model Card — AI Platform (api-gateway + chat-service), M6 demo

*This is a WORKED EXAMPLE showing what a completed Model Card looks like,
built on the shared demo app — not a template to copy verbatim. Every
number below except the Locust P95 was generated by an actual run during
this build (see the numbers' source noted in brackets); fill your OWN
system's real numbers when you do this for your own M3/M4/M5 capstone.*

## 1. Overview

- **System name:** AI Platform — api-gateway (chat + SQL assistant)
- **One-sentence description:** A FastAPI backend that answers product/order
  chat and SQL questions via Gemini, backed by Postgres, now hardened with
  JWT+API-key auth and a prompt-injection guardrail for production.
- **Owner / team responsible:** Trainer-provided demo system (Tredence GenAI cohort)
- **Date this card was written:** 13 Aug 2026

## 2. Intended Use

- **What is this system meant to be used for?** Answering natural-language
  chat and SQL questions about a demo product/orders dataset.
- **Who is the intended user?** Internal team members exploring the platform
  (a teaching demo, not a public product).
- **What should this system NOT be used for?** Anything outside the
  product/orders knowledge domain — it has no other data sources; questions
  outside scope get a plausible-sounding but unverified answer.

## 3. How It Works

- **What model powers it?** Gemini 2.5 Flash via Vertex AI, using the VM's
  own service-account identity — no API key stored in the app.
- **What does it have access to?** chat-service (Gemini), memory-service
  (Postgres-backed conversation history), sql-service (Postgres, read
  queries only).
- **Fallback if the main model is unreachable?** Yes — automatic fallback
  to a simulated reply, flagged via `served_by: "simulated"` in every
  response, so a failure is always visible, never silent.

## 4. Known Limitations

- **What can this system get wrong?** Questions outside the product/orders
  dataset will get a fluent-sounding answer that isn't grounded in real
  data — there's no refusal for out-of-scope questions yet.
- **Bias findings (Part 1/Step 5, AIF360, real run 13 Aug):** Disparate
  Impact = 0.341, Statistical Parity Difference = -0.436, Equal
  Opportunity Difference = -0.263 (against the shared `loan_approval_data.csv`
  — this app isn't a classifier itself, this audit demonstrates the
  methodology against the given synthetic dataset, per the M6 spec).
  A DI ratio this far below 0.8 (the common "four-fifths rule" reference
  point) would be a real fairness concern in a live decision system.
- **Red-team findings (Part 4/Step 4, real run against this deployed app,
  50 shared prompts):** 18/50 total blocked by the guardrail. Broken down
  by category — Prompt Injection 8/10, Jailbreak 8/10, PII/Data
  Extraction 1/10, Harmful Content 0/10, Scope Abuse 1/10. This guardrail
  is scoped to prompt-injection/jailbreak detection specifically (per the
  M6 spec's framing) — the 0% on Harmful Content is an honest scope gap,
  not a hidden failure: a content-safety layer would be a separate,
  future addition, noted here rather than silently absent.
